## Compact Rules

Pre-digested rules per skill. Delegators copy matching blocks into sub-agent prompts as `## Project Standards (auto-resolved)`.

### nodejs-backend-patterns
- Layering (project rule, `docs/cambio-de-stack.md` §3.1): routes (HTTP parse/validate only) → services (use cases) → domain (business rules) → repositories (SQL). No business logic or SQL inside routes.
- One centralized error handler: custom error classes; operational errors → 4xx with safe message, unexpected → 500 + logged stack; never leak internals.
- Validate all input at the route boundary (Zod/Joi); secrets only from env — `.env` never committed, `.env.example` without values.
- Structured logging (Pino/Winston) with context (requestId, consultorioId); never `console.log` in production paths.
- CORS with explicit origins (frontend domain only, never `*`); rate limiting via shared store; health-check endpoint; graceful shutdown; Postgres connection pooling.
- The skill's "use TypeScript" advice does NOT apply here — this project is JavaScript (Express 5, plain JS); skip TS-only guidance.

### backend-patterns
- REST: resource-based URLs, correct verbs for CRUD, query params for filtering/sorting/pagination; consistent JSON error shape across the API.
- Middleware pipeline for auth/logging/rate-limiting; JWT verification attaches `{ usuarioId, consultorioId, rol }` — `consultorio_id` comes from the token, NEVER from a client parameter (hard rule).
- Prevent N+1: batch fetches/joins instead of per-row queries; project only needed columns (no `SELECT *`).
- Index filters, FKs and `consultorio_id`; composite indexes matching query patterns.
- Multi-write operations (e.g. turnos overlap validation) run inside a single transaction.
- Centralized `ApiError(statusCode)` handler; validation failures → 400 with field messages.
- Rate limiting must use a shared store (Redis/gateway), not per-process in-memory counters.
- Structured logging with requestId; cache-aside only where a measured benefit exists — don't add caching speculatively.

### postgres-best-practices
- Target PostgreSQL 18 (Docker local + Neon cloud); standard SQL only — no vendor-specific features; run the latest minor release.
- Schema: precise data types, normalization, indexes on common filters (`consultorio_id`, status, FKs); composite/partial indexes for real query patterns.
- Migrations (project rule): numbered SQL files in `db/migrations/` (`001_pacientes.sql`, `002_turnos.sql`, …) that only advance — never edit a merged migration; no ORM auto-DDL; nobody alters tables by hand (skill is tool-neutral; do not introduce Flyway or any other migration tool).
- Query tuning: `EXPLAIN ANALYZE`, projection of needed columns only, sargable predicates.
- Transactions: keep short, choose isolation for concurrent writers, retry on serialization failure.
- Security: least-privilege roles, RLS where applicable; every tenant query filters `consultorio_id`.
- Load the matching `references/` file (schema-design, indexing, query-optimization, transaction-isolation) before deep work.

### sql-code-review
- Parameterized queries / prepared statements only — never string-concatenate SQL (injection).
- Least-privilege DB roles; audit sensitive operations; never expose sensitive columns (patient data) via `SELECT *`.
- Explicit JOINs (no comma joins); sargable date filters (range predicates, not functions on the column).
- Index review: missing indexes on filter/join columns and over-indexing that hurts writes.
- Standards: consistent naming, explicit column lists, no destructive statements (DROP/TRUNCATE) reachable from app code.
- Review migration SQL in `db/migrations/` with the same bar: additive, numbered, never edited once merged.

### javascript-testing-patterns
- Runner: Jest or Vitest on Node; the whole suite runs with `npm test` (hard rule — tests green before any PR).
- Cover EVERY spec scenario: ≥3 tests per spec — happy path, business error, edge case (e.g. back-to-back turnos are valid, overlap is not).
- Domain rules unit-tested; route→repository integration tests run against a real PostgreSQL (docker compose test DB) — do not mock the SQL layer.
- Mock only external boundaries (network, clock, third-party APIs).
- Fixtures are always fictitious — NEVER real patient data (hard rule).
- Tenant isolation tests mandatory: a user from consultorio A must not read or modify consultorio B's data.
- Keep tests fast, isolated and deterministic; no shared mutable state between tests.

### tdd
- Red → green: write the failing test first, then only enough code to pass; one vertical slice (one test → one implementation) per cycle.
- Test behavior through public interfaces (routes/services), never internals or private methods.
- Confirm the test seams up front with the user; no tests at unconfirmed seams.
- Anti-patterns: implementation-coupled mocks, tautological assertions (expected values from an independent source: spec/literal), horizontal slicing (all tests before any implementation).
- Refactoring belongs to the review stage, not the red→green loop.
- Project framing: `npm test` is the gate; ≥3 scenarios per spec (feliz / error de negocio / borde).

### multi-tenant-architecture
- Skill targets Cloudflare/Vercel platforms — for this Node.js/Express project apply the PRINCIPLES (isolation, routing, context propagation), not the platform-specific configs.
- Workflow order: domain strategy/PSL → tenant identification → isolation model → deterministic routing → context propagation → least-privilege bindings → custom domains → limits-to-plans.
- Data isolation default: shared schema with the tenant column on EVERY tenant-aware table (`tenant_id` in the skill; in this project `consultorio_id`, from the token, never from the client) + RLS where available; DB-per-tenant only for regulated/noisy tenants.
- Delete/overwrite all inbound `x-tenant-*` headers on every path; the proxy resolves routing, NEVER authorization — the data layer must re-derive and enforce the tenant.
- Tenants never influence routing; unknown hostname → 404 (never the brand site).
- Custom domains need a full recorded lifecycle: DNS target → ownership verify → certificate → activation → removal/failure path.

### docker-compose-patterns
- Canonical filename `compose.yaml` (not `docker-compose.yml`); dev-only settings in `compose.override.yaml`.
- Pin image tags to a specific version — never `latest` or omitted (e.g. `postgres:18`).
- `depends_on` with `condition: service_healthy` only where the dependency has a `healthcheck`; DB services always get one (e.g. `pg_isready`; start `interval: 5s, timeout: 3s, retries: 3, start_period: 10s`).
- Distroless/scratch images have no shell: use a healthcheck sidecar with `network_mode: "service:<app>"` and depend on the sidecar.
- Named volumes for persistent data; bind mounts only for dev source sync; no Docker socket mounts without genuine need.
- Secrets via `env_file:` or `${VAR:-default}` substitution — never plaintext passwords in `compose.yaml`; keep `.env` in `.gitignore`.
- Destructive commands (`down -v`, `volume rm/prune`, `compose rm -v`) require stating the data loss and getting explicit user confirmation; restart with plain `down`/`restart`.
- Validate with `docker compose config --quiet` (skill script `scripts/verify-compose.sh`) — quiet mode avoids leaking interpolated credentials.

### security-review
- Report ONLY HIGH-confidence findings: vulnerable pattern + attacker-controlled input confirmed after research. Never flag on pattern matching alone.
- Research the whole codebase (data flow, upstream validation, config, framework protections), but report only the file/diff the user provided.
- Confidence gates: MEDIUM (input unclear) → note "Needs verification"; LOW/theoretical/best-practice → do NOT report.
- Do not flag: test/dead code, constants and server-controlled values (env, config, settings), or framework-mitigated patterns (auto-escaping, ORM parameterization) — unless explicitly bypassed (`|safe`, `dangerouslySetInnerHTML` with user input, `.raw()`).
- Always flag (critical): `eval(exec)(user_input)`, `child_process.exec` with user input, unsafe deserialization (`pickle.loads`, `yaml.load` without SafeLoader, PHP `unserialize`), `shell=True`.
- Classify severity by exploitability + impact (Critical/High/Medium/Low); load the matching `references/` guide (injection, ssrf, xss, auth...) and language guide before judging.

### openspec-propose
- PLANNING ONLY: never edit project code or start apply in the same response; present artifacts, stop, wait for a new request.
- Before any write: `openspec list --json` must show a root — `"root": null` + auto-selected → stop and answer normally; explicit OpenSpec request → ask before `openspec init`. NEVER create `openspec/` as a side effect.
- `openspec context --json` gives the authoritative root; apply `openspec/config.yaml` `context` field (≤51,200 bytes UTF-8) as constraints — do NOT copy context/rules into artifacts.
- Flow: `openspec new change "<kebab-name>"` → loop `openspec status --change --json` + `openspec instructions <artifact> --change --json` → create the full required set (transitively via `requires` edges, not just `apply.requires`).
- Use the returned `template` and `resolvedOutputPath` (must stay inside `changeRoot`); verify each file exists after writing; re-read dependency artifacts from disk every time.
- Ask the user on ambiguity that materially affects scope/behavior/acceptance criteria; minor details → reasonable assumption recorded in artifacts. If the change already exists, ask continue vs. new.

### openspec-apply-change
- Announce "Using change: <name>" + how to override; then `openspec status --change --json` and `openspec instructions apply --change --json`.
- Handle states: `blocked` → show message, complete missing artifacts first (never start implementing); `all_done` → report complete; otherwise proceed.
- Read every path in `contextFiles` before starting. Treat `context` as required prompt input and `operationGuidance` as advisory — neither proves a task is done nor bypasses a blocked state.
- Task loop: confirm the checkbox at `sourcePath`/`line` still matches → implement → mark `- [x]` only when fully implemented → rerun apply instructions to confirm progress changed.
- Pause on: ambiguity, blockers, design issues revealed, or scope beyond the spec — surface added scope and ask; never silently narrow, defer, or drop specified behavior.

### openspec-archive-change
- Check first: `openspec status` (artifacts must be `done`/`skipped`) and `openspec list --json` task counts (CLI counts only `x`/`X`); warn + get user confirmation if incomplete; on lookup failure → report and stop.
- Assess delta sync state from `artifactPaths.specs.existingOutputPaths` ONLY; compare each delta against its main spec; missing main spec is not "already synced".
- Sync-blocked capabilities (MODIFIED/RENAMED on a missing main spec, REMOVED-only without `retire_capabilities: true`) → offer only "Archive without syncing" / "Cancel".
- If syncing: fetch `openspec instructions specs` rules once, run the sync INLINE and synchronously (never background — archive would move `changeRoot` mid-sync), verify main-spec structure, then re-compare ALL capabilities; any mismatch or sync failure → STOP, do not archive.
- Archive = move `changeRoot` to `<changesDir>/archive/YYYY-MM-DD-<name>` (no stacked dates); fail if the target already exists.

### openspec-sync-specs
- Agent-driven intelligent merge: read each delta spec, edit the main spec directly; preserve everything the delta does not mention.
- Delta spec paths come ONLY from `artifactPaths.specs.existingOutputPaths` — never infer them; honor caller-narrowed subsets verbatim and never widen.
- New capability (main spec missing): only ADDED requirements may be applied; copy the delta's `## Purpose` verbatim; never invent a missing requirement; MODIFIED/RENAMED block, REMOVED-only requires `retire_capabilities: true`.
- NEVER write or leave an empty `## Requirements` section; capability retirement (file delete) requires ALL six listed conditions including the `.openspec.yaml` marker.
- Fetch `openspec instructions specs --change --json` once before the first main-spec write; apply `rules` as constraints only — never copy rule text into specs or summaries.
- Validate with `openspec validate --specs`; if it fails, report the problems and do not claim the sync succeeded.

### openspec-update-change
- Planning artifacts only — NEVER edit implementation code; if the revision implies code changes, stop and point to `openspec-apply-change`.
- Use artifact ids and paths from `openspec status --json` (`existingOutputPaths`) — never hardcoded artifact names; never write to a glob `resolvedOutputPath`.
- Draft the edit in conversation first, then reconcile EVERY existing artifact against it in any direction (build order is a reading order, not a constraint).
- Show each proposed revision and why; write only after user confirmation; a rejected revision leaves the file untouched.
- Do not advance the build frontier: missing `ready`/`blocked` artifacts are a separate step (point to `openspec instructions`); `skipped` artifacts stay untouched. Only new-file scope: a confirmed concrete path under a partly-populated glob artifact.
- If the request changes the change's intent rather than refining it → recommend a new change name instead.

### openspec-explore
- A STANCE, not a workflow: thinking partner. Read files/search/run read-only commands freely; NEVER write code or implement — implementation requests go to `openspec-propose`.
- Writing OpenSpec change artifacts is allowed only after an explicit yes/no confirmation naming the exact files; an explicit "capture this as a change" request counts as that confirmation.
- One focused question at a time (why it matters + which decision it unlocks); grounded in actual codebase inspection; never ask facts you can verify yourself.
- Curious, open threads, patient; ASCII-only diagrams (`+ - | --> ^ v * x`) — Unicode box glyphs drift across terminals.
- Track decisions in the conversation, not files; silence is not acceptance; answering ≠ permission to write; keep file-write confirmation separate from discovery.
- Same OpenSpec root/store guardrails as the other workflows (never create `openspec/` as a side effect).

### skill-creator
- Capture intent first (what it enables, when it triggers, expected output, testability) — extract from conversation history if the user says "turn this into a skill"; confirm before proceeding.
- SKILL.md frontmatter: `name` + `description` are the trigger mechanism — put ALL "when to use" info in the description and make it "pushy" (skills undertrigger).
- Progressive disclosure: metadata always in context; body <500 lines ideal (add references/ with clear pointers beyond that); `scripts/` `references/` `assets/` loaded as needed; >300-line references get a TOC.
- Iterate: draft → test prompts → run with skill → qualitative + quantitative evals → rewrite → expand test set; use the description improver for triggering accuracy.
- No malware/exploit content (principle of lack of surprise); imperative instructions; match the user's jargon level.

### emil-design-eng
- UI reviews MUST use a single markdown table with `| Before | After | Why |` columns — never a Before/After list.
- Animation decision framework: never animate high-frequency/keyboard actions (100+/day → no animation; tens/day → remove or reduce); every animation needs a stated purpose (spatial consistency, state indication, feedback).
- Easing: entering/exiting → ease-out; on-screen movement → ease-in-out; hover/color → ease; constant motion → linear; always custom `cubic-bezier` (built-ins are too weak, e.g. `cubic-bezier(0.23, 1, 0.32, 1)`).
- Animate only `transform`/`opacity` — never `top/left/width/height`; specify exact transition properties, never `transition: all`.
- `:active` states required on buttons (e.g. `scale(0.97)`); popovers scale from their trigger; elements never appear from nothing (`scale(0.95)` + opacity).
- Taste is trained: study why great interfaces feel good; unseen details compound.
